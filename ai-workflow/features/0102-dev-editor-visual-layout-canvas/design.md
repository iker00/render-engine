# Design: Feature 0102 - dev-editor-visual-layout-canvas

## Contexto

El drawer de `DevRuntime` hoy sostiene dos piezas de estado separadas en `DevRuntimeReady` (`src/dev-runtime/dev-runtime.tsx`):

- `editorBuffer`: texto crudo del editor Monaco.
- `currentConfig`: el `RuntimeConfig` ya validado, que es la única fuente de verdad que consume `RuntimeStateProvider` y por tanto todo lo que se renderiza (tanto el preview del runtime como, con esta feature, el canvas visual).

Ambos solo se reconcilian en la acción "Aplicar" (`handleApply`): `JSON.parse` del buffer → `validateRuntimeConfig` → si es válido, `migrateRuntimeStateAcrossConfig(prevState, currentConfig, nuevoConfig, { dataValues })` a través de `DevRuntimeStateBridge` (`getLatestState` / `dispatchAndSyncState` sobre `RuntimeStateContext`) → `flushSync` actualiza `currentConfig`. Este mismo patrón de tres pasos (migrar estado → dispatch por el bridge → commit de `currentConfig`) se repite exactamente en otros dos sitios: el efecto de cambio de prop inicial y la recarga por HMR. No existe hoy ningún cuarto punto de entrada a esa secuencia.

El renderizado de `layout` pasa por un único dispatcher: `layout-node-renderer.tsx`, un `switch (node.type)` de ~25 casos que resuelve el componente desde `NodeComponents` (`nodes/node-components-map.ts`) y, tras el switch, envuelve el resultado de forma uniforme en `<LazyNode>` más un `<div>` opcional de grid-span. Ese punto posterior al switch es el único lugar transversal a todo el catálogo sin tocar cada nodo individual.

Los schemas Zod por tipo de nodo (`containerNodeSchema`, `buttonNodeSchema`, `tableNodeSchema`, etc.) ya existen de forma individual en `runtime-config-zod.ts` y se combinan en `runtimeConfigRootSchema`. Hoy solo se deriva JSON Schema del schema raíz completo (`dev-runtime-json-schema.ts`, usado para el autocompletado de Monaco); no existe todavía derivación por schema individual.

**Divergencia entre forma cruda y forma normalizada (relevante para la Decisión 5)**: `handleApply` (`src/dev-runtime/dev-runtime.tsx`, líneas ~237-247) deja `editorBuffer` intacto tras un "Aplicar" exitoso, con un comentario inline explícito: re-serializar `validation.config` (la forma ya normalizada) rompería un segundo "Aplicar" sobre ese mismo texto, porque el validador exige `preloads` en forma cruda (`{ "operationName": {...} }`, una clave dinámica) y la normalización interna la convierte en `{ operationName, requestParams }` (dos claves fijas), que `validatePagePreloads` rechaza explícitamente como entrada. Una auditoría específica para esta feature (ver Decisión 5) confirma un segundo caso, más grave porque falla en silencio en vez de lanzar error: `form.submitAction.onSuccess`/`form.submitAction.onError` se autoran anidados dentro de `submitAction`, pero `validateFormSubmitAction` (`src/config/validate-actions-visibility.ts`) los extrae y `validateFormNode` los reasigna como campos hermanos de `submitAction` en el `FormLayoutNode` normalizado (coherente con el tipo `FormLayoutNode` de `runtime-config-types.ts`, donde `onSuccess`/`onError` son campos de nivel superior del nodo, no de `submitAction`). Si ese `FormLayoutNode` normalizado se serializa tal cual y se revalida, `formNodeSchema` (`.strip()`, sin declarar `onSuccess`/`onError` a ese nivel) los descarta silenciosamente sin error — comportamiento ya cubierto por un test existente del proyecto (`runtime-config-validation-forms-semantics.test.ts`, caso "silently discards onSuccess at root form node"). Ningún otro punto de `layout` (colecciones de `repeater`/`list`/`select`/`radioGroup`/`checkboxGroup`, filas dinámicas de `table`, mutua exclusión `src`/`fetch` de `image`) tiene este problema: sus formas normalizadas son puntos fijos válidos como reentrada. Tampoco existe ningún `.default(...)` en `src/config/*.ts` que inyecte claves no presentes en el JSON crudo original.

Las reglas de qué nodo puede anidarse dentro de qué otro están repartidas de forma desigual en `src/config/validate-layout-nodes.ts`: `modalAllowedChildTypes` y `linkAllowedChildTypes` ya son `Set<string>` reutilizables como predicados puros; el resto (qué tipos aceptan `children` en absoluto, que `input`/`textarea`/`select`/`radioGroup`/`checkboxGroup` solo sean válidos dentro de `form`, que `button` sin `action` exija estar dentro de `form`, que `repeater` rechace `children`) vive embebido dentro de funciones grandes de validación que también hacen parsing Zod y construcción de mensajes de error, no reutilizables de forma aislada.

## Objetivos / No objetivos

### Objetivos
- Definir cómo el canvas de edición visual se integra con el modelo de estado ya existente (`currentConfig` / bridge / migración) sin introducir una segunda fuente de verdad paralela.
- Definir el punto de extensión concreto en el renderer de producción para soportar selección, hover y drop, sin duplicar el dispatcher de nodos ni degradar el render de producción.
- Fijar el mecanismo de generación del formulario de propiedades a partir de los schemas Zod ya existentes.
- Fijar la estrategia de drag-and-drop (`dnd-kit`) para un modelo de manipulación directa sobre el DOM renderizado, no sobre una lista.
- Resolver el comportamiento del canvas ante un Monaco momentáneamente inválido, reutilizando el modelo de commit ya vigente en vez de inventar uno nuevo.
- Extraer las reglas estructurales de anidamiento a predicados puros reutilizables, sin duplicar lógica de validación.

### No objetivos
- No se diseña la edición visual de `api`, `pages`, `tokens` ni `translations` (features posteriores).
- No se diseña deshacer/rehacer; queda fuera de alcance según la spec.
- No se cambia el contrato observable del runtime en producción, su schema Zod, ni la frontera de activación de `DevRuntime`.
- No se diseñan los pickers contextuales de referencias string (`queries.x`, `forms.x`, etc.); el formulario de propiedades trata esos campos como texto libre, igual que el resto de la spec deja fuera de alcance.

## Decisiones

### 1. El canvas se renderiza reutilizando el renderer de producción, no un renderer paralelo
El canvas monta el mismo `LayoutRenderer`/`layout-node-renderer.tsx` que usa el preview de producción, dentro de un nuevo `LayoutEditModeContext` (activo únicamente dentro del árbol del canvas). Esto garantiza fidelidad visual exacta con lo que verá el usuario final y evita el riesgo de que un renderer duplicado del catálogo de ~25 nodos vaya divergiendo con el tiempo.

**Alternativa descartada**: construir un renderer de edición independiente que interprete `layout` sin pasar por `layout-node-renderer.tsx`. Se descarta porque duplicaría el switch de 25 casos y su mantenimiento, violando la responsabilidad ya fijada en `architecture.md` de que `layout-renderer`/`layout-node-renderer` son "el borde central de render".

**Trade-off asumido**: `layout-node-renderer.tsx` es código compartido con producción; cualquier cambio ahí conlleva riesgo de regresión en el renderer de producción si no queda bien acotado (ver Riesgos).

### 2. Punto de extensión: wrapper post-switch en `layout-node-renderer.tsx`, activado por contexto
Inmediatamente después del `switch (node.type)` existente (mismo punto donde hoy se aplica `<LazyNode>` y el `div` de grid-span), se añade un wrapper condicional que solo actúa si `LayoutEditModeContext` está presente:
- añade `data-node-path` (ver Decisión 5) al elemento resultante,
- añade `onClick` (selección) y `onMouseEnter`/`onMouseLeave` (hover) capturados en fase de burbuja normal, sin `stopPropagation` sobre los hijos, para no romper controles interactivos internos (orden de tabla, inputs de formulario, etc.),
- cuando el contexto está ausente (todo uso fuera del canvas, incluyendo producción), el wrapper es un no-op: mismo output que hoy.

**Riesgo residual**: aunque el wrapper es inerte sin el contexto, sigue siendo un cambio en un fichero compartido con producción. Mitigación: cobertura de test explícita que verifique que el output de `layout-node-renderer` es byte-a-byte idéntico al actual cuando `LayoutEditModeContext` no está presente.

### 3. Direccionamiento de nodos: `path` estructural, no `id`
Cada nodo se direcciona por un `path`: array de pasos `{ field: 'children' | 'template', index? }` desde la raíz de `layout` de la página. `template` es el paso especial usado para entrar en `repeater.props.template` (que es un único nodo, no un array). Este `path` es la clave para selección, breadcrumb, y como argumento de las funciones puras de mutación (Decisión 4). No se introduce un campo `id` sintético persistido en el JSON: el `path` se recalcula en cada render a partir de la posición real en el árbol, evitando divergencia entre "id declarado" y "posición real" tras un reordenamiento.

**Trade-off**: un `path` posicional se invalida si la estructura cambia entre el momento de calcularlo y el de usarlo (p. ej. drag que dispara dos renders). Mitigación: las operaciones de mutación (Decisión 4) son síncronas y basadas en el `currentConfig` vigente en el momento del evento, no en un `path` cacheado de un render anterior.

**Precisión sobre el threading de `path` en nodos con render anidado propio** (detectada en `review-implementation-plan`, séptima pasada): `repeater`, `accordion` y `tabs` no pasan por la recursión de nivel superior de `layout-renderer.tsx` para sus propios hijos — cada uno invoca su propio `<LayoutRenderer>` internamente sobre una colección que no siempre cuelga de `field: 'children'` (`props.template` para `repeater`, `props.items[itemIndex].children` para `tabs`). Esto exige dos piezas adicionales, no solo el tipo de dato del `path`: (a) `LayoutRenderer` necesita un mecanismo para construir el paso de cada hijo con un `field` distinto de `'children'` cuando quien lo invoca lo requiere (no solo un `path` base), y (b) `layout-node-renderer.tsx` debe pasar `path` a `RepeaterNode`/`AccordionNode`/`TabsNode` en su `switch`, cosa que hoy no hace. Ambos detalles quedan resueltos como parte del plan de implementación (no cambian la decisión de fondo: sigue siendo un `path` estructural recalculado en cada render, no un `id`).

**Precisión adicional sobre `container`/`form`/`modal`/`link`** (detectada en `review-implementation-plan`, octava pasada): estos cuatro tipos sí quedan cubiertos por la recursión de nivel superior de `layout-renderer.tsx` — pero esa recursión tiene, dentro de sí misma, dos usos del `path` calculado por nodo que deben coexistir: uno para identificar al propio nodo (pasado a `LayoutNodeRenderer`) y otro para que la llamada recursiva interna que construye sus `children` acumule correctamente la profundidad en el siguiente nivel. Omitir el segundo uso no rompe la selección del nodo de primer nivel, pero sí colapsa a un único nivel el `path` de cualquier nodo anidado dos o más niveles por debajo (el caso central de la spec, `container > form > heading`). El plan de implementación debe dejar esto explícito en la propia recursión, no darlo por cubierto implícitamente.

### 4. Mutaciones del árbol como funciones puras en `src/dev-runtime/`
Se introduce un módulo nuevo (p. ej. `src/dev-runtime/layout-tree-mutations.ts`) con funciones puras `movePathTo(pageLayout, fromPath, toPath)`, `insertNodeAt(pageLayout, path, newNode)`, `removeNodeAt(pageLayout, path)`, cada una operando sobre el array `layout` de una página y devolviendo un array nuevo (sin mutar in-place). Vive en `src/dev-runtime/` y no en `src/config/` ni `src/runtime/`, porque es lógica exclusiva de la herramienta de desarrollo, no del contrato ni del render del runtime en producción.

Cada mutación, antes de comprometerse, se valida con las nuevas funciones puras de reglas estructurales (Decisión 6) y, tras eso, con `validateRuntimeConfig` sobre el documento completo resultante — reutilizando exactamente la misma validación que ya usa "Aplicar", en vez de confiar solo en la validación local del punto de drop.

### 5. Commit de una mutación del canvas reutiliza el pipeline de validación/migración de "Aplicar"; la serialización a texto parchea solo `layout`, no reserializa el documento completo
Una mutación del canvas ya produce un objeto `RuntimeConfig` válido en memoria (no texto). El flujo de commit es:
1. calcular el nuevo config candidato con una función de Decisión 4,
2. `validateRuntimeConfig(candidato)` (mismo validador, ninguna validación paralela divergente),
3. si es válido: `migrateRuntimeStateAcrossConfig` + dispatch por `DevRuntimeStateBridge` + `flushSync` de `currentConfig` — idéntico al paso 3-4 de `handleApply`,
4. **actualizar el texto de Monaco parcheando, no reserializando el documento completo** (ver más abajo por qué).

**Corrección respecto a una versión anterior de esta decisión** (detectada por `review-implementation-plan` durante la planificación de implementación de esta misma feature): una versión previa de este paso 4 decía "re-serializar el nuevo config a texto formateado", describiéndolo como "idéntico" al pipeline de `handleApply`. Es incorrecto — `handleApply` explícitamente **no** reserializa (ver Contexto): mantiene `editorBuffer` como el texto que acaba de validar, precisamente porque reserializar el `RuntimeConfig` normalizado completo rompe la forma cruda de `preloads` y descarta en silencio `form.onSuccess`/`form.onError`. "Aplicar" puede permitirse mantener el buffer intacto porque el buffer ya era el texto crudo válido que produjo ese mismo `currentConfig`. El canvas no tiene ese lujo: por requisito de la spec (FR12), sus mutaciones deben reflejarse de inmediato en el texto de Monaco, así que "no tocar el texto" no es una opción — hace falta una estrategia de serialización explícita que evite las dos divergencias de Contexto.

**Estrategia elegida — parchear solo la clave `layout` de la página activa dentro del último texto crudo válido conocido**:
- Se introduce un nuevo estado en `DevRuntimeReady`, `lastValidConfigText: string`, con el invariante "es el texto crudo exacto que, al parsear y validar, produce el `currentConfig` vigente". Se inicializa a `initialConfigText` y se actualiza en los tres puntos donde hoy se actualiza `currentConfig` (efecto de cambio de prop inicial, HMR, `handleApply`) más el nuevo punto de esta decisión — en los tres casos existentes, el nuevo valor es exactamente el texto crudo que ya se acababa de validar en ese punto (no hay reserialización nueva ahí). **Precisión sobre el punto de HMR** (el invariante está atado a `currentConfig`, no a `editorBuffer`): `activeConfigHmrApply` actualiza `currentConfig` de forma incondicional dentro de su `flushSync`, pero solo actualiza `editorBuffer` cuando no hay cambios pendientes en Monaco (para no pisar una edición sin aplicar). `lastValidConfigText` debe seguir el mismo régimen que `currentConfig` en ese punto — actualizarse siempre, nunca solo cuando `editorBuffer` también se actualiza — porque de lo contrario un HMR con cambios pendientes seguido de un commit del canvas parchearía sobre un texto crudo pre-HMR obsoleto, reintroduciendo la misma clase de divergencia que esta decisión existe para evitar.
- El commit del canvas construye el nuevo texto así: `rawConfigObject = JSON.parse(lastValidConfigText)`; reemplaza `rawConfigObject.pages[activePageIndex].layout` por la representación serializable del nuevo árbol `layout` mutado (ver "Denormalización de `form`" abajo); `JSON.stringify(rawConfigObject, null, 2)`. El resto del documento (`api`, `initialPage`, `tokens`, `translations`, `preloads` de cualquier página, título, etc.) se copia verbatim del texto crudo ya válido — nunca se reserializa desde `currentConfig`, así que `preloads` conserva su forma cruda de una sola clave sin que esta decisión necesite tocarlo.
- El resultado se escribe tanto en `editorBuffer` (lo que ve Monaco) como en `lastValidConfigText` (para que el próximo commit — de Monaco o del canvas — parta de un texto crudo consistente).
- **Denormalización de `form`**: dado que la única divergencia confirmada *dentro de* `layout` es `form.onSuccess`/`form.onError` (ver Contexto), la función que serializa el árbol `layout` mutado a JSON aplica un paso de denormalización acotado: para cada nodo `form` con `onSuccess` y/o `onError` declarados, los anida de vuelta dentro de `submitAction` (`submitAction: { ...submitAction, onSuccess, onError }`) antes de serializar, y omite los campos `onSuccess`/`onError` de nivel superior del nodo. Es la única transformación de este tipo necesaria — el resto del catálogo de nodos son puntos fijos confirmados por la auditoría de Contexto.
- **Edición concurrente en Monaco**: si el usuario tiene cambios sin aplicar en Monaco (`hasPendingChanges: true`) en el momento de un commit del canvas, el commit del canvas **sobrescribe** ese texto pendiente con el nuevo texto parcheado (y resetea `hasPendingChanges` a `false`). Es una decisión deliberada, no un descuido: a diferencia de HMR (que respeta cambios pendientes porque su origen es externo a la sesión — un fichero editado fuera del navegador), una mutación del canvas es una acción del usuario dentro de la misma sesión de edición, más parecida en naturaleza a "Aplicar" (que también reemplaza el estado vigente) que a HMR. Alternativa descartada: preservar el texto pendiente de Monaco e ignorar el commit del canvas hasta que el usuario resuelva su edición manual — se descarta porque contradice el requisito de reflejo inmediato de la spec (FR12) sin aportar ninguna protección real (el usuario puede ver y deshacer el cambio del canvas leyendo el nuevo texto).

Esto reutiliza el pipeline de validación/migración/commit de estado ya existente (documentado en Contexto) para los pasos 1-3, y resuelve el paso 4 con una estrategia de serialización nueva pero acotada, en vez de crear un cuarto punto de entrada con semántica de estado propia.

**Alternativa descartada**: mantener el canvas como una vista "optimista" desacoplada que solo escribe a Monaco y espera a que el usuario pulse "Aplicar" para reflejarse en el runtime. Se descarta porque contradice el requisito de la spec de reflejo inmediato canvas→Monaco→runtime, y porque introduciría una tercera fuente de verdad temporal.

**Alternativa descartada para el paso 4**: reserializar el `RuntimeConfig` candidato completo (la versión anterior de esta decisión). Se descarta por las dos divergencias confirmadas en Contexto (`preloads`, `form.onSuccess`/`form.onError`), la segunda de las cuales falla en silencio sin siquiera un error de validación detectable.

### 6. Reglas estructurales extraídas a predicados puros reutilizables
Se extraen a un módulo común en `src/config/` (p. ej. `layout-placement-rules.ts`) las reglas hoy dispersas: qué tipos aceptan `children` (`container`, `form`, y los ya existentes `modalAllowedChildTypes`/`linkAllowedChildTypes` como casos con catálogo cerrado propio), qué tipos exigen estar dentro de un `form` (`input`, `textarea`, `select`, `radioGroup`, `checkboxGroup`, y `button` sin `action`), y que `repeater` no acepta `children`. `validate-layout-nodes.ts` pasa a consumir estos predicados en vez de repetir la lógica inline, y el validador de drop-target del canvas consume exactamente los mismos predicados. Esto es un refactor acotado de una validación ya existente, no una reescritura de `src/config/`.

**Riesgo**: este refactor toca un módulo de validación central (`src/config/`) usado por todo el proceso de bootstrap. Mitigación: cambio de extracción pura (mover condiciones existentes a funciones con nombre, sin cambiar su resultado), cubierto por la suite de tests de validación ya existente antes de escribir ningún test nuevo específico del canvas.

### 7. Drag-and-drop con `@dnd-kit/core` (no `@dnd-kit/sortable`)
Se confirma `dnd-kit` como librería de arrastre, según la preferencia ya indicada. Para el modelo de manipulación directa sobre el render (no una lista), se usan las primitivas de bajo nivel `@dnd-kit/core` (`useDraggable`, `useDroppable`, sensores, detección de colisión personalizada) en vez de `@dnd-kit/sortable`, que asume una lista ordenada de items intercambiables y no encaja con drop-zones calculadas contra un árbol de layout con anidamiento y `span` responsive. Las zonas de drop se derivan directamente de los elementos con `data-node-path` ya expuestos por la Decisión 2 (cada contenedor/form, incluyendo su placeholder vacío, y cada posición entre hermanos, son droppables independientes), y la validez del destino se resuelve contra los predicados de la Decisión 6 antes de aceptar el `onDragEnd`.

**Riesgo residual**: calcular geometría de drop contra nodos con `span` responsive variable (columnas de grid) es más complejo que una lista vertical simple; el diseño no fija todavía el algoritmo exacto de "sobre qué mitad de qué celda estoy soltando" — queda para el plan de implementación acotarlo nodo por nodo si hace falta.

### 8. Formulario de propiedades: renderer propio dirigido por JSON Schema por nodo
Cada schema Zod individual ya existente (`containerNodeSchema`, `buttonNodeSchema`, etc.) se convierte a JSON Schema con `toJSONSchema()` (la misma API ya usada hoy para Monaco, sin librería externa nueva), pero invocada por schema individual en vez de sobre el root completo. Un nuevo dispatcher de campos (análogo en espíritu a `NodeComponents`) mapea las primitivas del JSON Schema resultante (`string`, `number`, `boolean`, `enum`, `array`, `object`) a un catálogo fijo y pequeño de componentes de campo en Tailwind (input de texto, input numérico, checkbox, select para enum, sección repetible para arrays/objetos anidados como `table.props.columns`).

**Alternativa descartada**: una librería de formularios sobre JSON Schema (p. ej. `react-jsonschema-form`/`@rjsf/core`). Se descarta porque trae su propio sistema de theming que exigiría override profundo para encajar con Tailwind (conflicto directo con `conventions.md`, que desaconseja introducir una API visual paralela al sistema de utilidades ya establecido), es una dependencia considerable para un catálogo acotado de ~25 tipos de nodo, y no sigue el patrón arquitectónico ya establecido de dispatcher propio por discriminador.

**Trade-off asumido**: mantener este dispatcher de campos es trabajo propio del proyecto, no delegado a una librería madura; a cambio, queda completamente alineado con Tailwind y con el patrón de dispatcher ya usado en el resto del código.

### 9. Contenedores vacíos: placeholder inyectado solo en modo edición
El wrapper de la Decisión 2, cuando detecta `type: 'container' | 'form'` con `children` vacío o ausente y `LayoutEditModeContext` activo, renderiza un `div` con borde punteado y etiqueta en vez de nada. Esto vive enteramente en el wrapper condicional al contexto: el render de producción (contexto ausente) sigue sin mostrar nada para un contenedor vacío, sin ninguna rama de código nueva en ese camino.

### 10. `repeater` en modo edición: fuerza exactamente una iteración de `props.template`
El caso `repeater` de `layout-node-renderer.tsx`, cuando `LayoutEditModeContext` está activo, no expande la colección resuelta N veces: renderiza `props.template` exactamente una vez, con un `item.*` sintético (primer elemento real si la colección resuelta tiene datos, o un objeto de ejemplo derivado del propio schema si está vacía). Es un cambio acotado al caso `repeater` del dispatcher, coherente con que `repeater` ya es "expansión estructural sin wrapper visual propio" (`architecture.md`): en modo edición dejamos de expandir, pero seguimos usando el mismo mecanismo de contexto `item.*` ya existente para una sola iteración.

### 11. Comportamiento ante Monaco momentáneamente inválido: se resuelve por el modelo ya vigente, no por un caso especial nuevo
El canvas renderiza siempre `currentConfig`, exactamente igual que el preview de producción. Como `currentConfig` **ya** solo se actualiza tras una validación exitosa (ver Contexto: `handleEditorChange` nunca toca `currentConfig`), el canvas automáticamente se queda congelado en el último estado válido mientras el texto de Monaco está sintácticamente incompleto o no valida — sin necesidad de ningún estado especial nuevo. Esto responde a la pregunta abierta de la spec sin introducir comportamiento adicional: el canvas hereda gratis la misma garantía que ya protege al preview de producción.

**Consecuencia explícita para la spec**: la redacción "cualquier cambio aplicado desde Monaco se refleja de inmediato en el canvas" debe leerse, como ya matiza el criterio de aceptación de la spec, como "tras Aplicar con éxito" — no por cada pulsación de tecla en Monaco. No se propone ningún cambio a `spec.md` porque el criterio de aceptación relevante (FR13) ya está redactado en esos términos; esta decisión solo fija la causa técnica.

## Riesgos y trade-offs

- **Cambio en fichero compartido con producción** (`layout-node-renderer.tsx`): mitigado por diseño condicional al contexto (Decisión 2) y por exigir en el plan de implementación un test que congele el output actual sin contexto antes de tocar el fichero.
- **Refactor de reglas estructurales** (`src/config/validate-layout-nodes.ts`): mitigado por tratarse de extracción pura cubierta por tests de validación ya existentes.
- **Geometría de drop contra layout responsive**: no completamente resuelta en este design (ver Decisión 7); el plan de implementación deberá acotar el algoritmo de colisión nodo por nodo, empezando por los casos más simples (listas verticales de hermanos) antes de abordar grids con `span`.
- **Dispatcher de campos propio para formularios**: es superficie de código nueva a mantener a medida que el catálogo de nodos crezca; mitigado por ser un catálogo cerrado de primitivas JSON Schema (no un lenguaje de formularios genérico) y por reutilizar exactamente los schemas Zod ya mantenidos por el resto del proyecto.
- **`repeater` en modo edición con datos de ejemplo sintéticos**: si el schema no permite derivar un objeto de ejemplo razonable para una colección vacía (tipos muy abiertos), el formulario de propiedades de los nodos dentro del template podría no tener con qué previsualizar interpolaciones `{{item.*}}`. Riesgo aceptado como limitación conocida, no bloqueante para el resto de la feature.
- **Denormalización acotada de `form.onSuccess`/`form.onError` (Decisión 5)**: la estrategia de serialización del canvas depende de una lista cerrada y auditada de divergencias raw/normalizado dentro de `layout` (hoy: solo `form`). Si una feature futura añade un nodo o campo nuevo con una divergencia análoga (un shape crudo que la validación reconstruye de forma distinta), la función de denormalización de esta feature quedaría incompleta de forma silenciosa para ese caso nuevo, replicando el mismo tipo de pérdida de datos ya identificado para `form`. Mitigación: la función de denormalización debe documentarse explícitamente como "lista cerrada, revisar al añadir cualquier normalización nueva en `src/config/validate-*.ts`" en el propio código, no solo aquí.

## Migración o despliegue
